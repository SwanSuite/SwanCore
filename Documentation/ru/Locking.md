# Архитектурная спецификация синхронизации SwanCore

## Обзор

Движок синхронизации `SwanCore` представляет собой ультравысокопроизводительный, потокобезопасный и эффективный с точки зрения памяти уровень изоляции выполнения, оптимизированный для современных многопоточных сред. Благодаря глубокой интеграции с механизмами безопасности Swift, эта архитектура полностью устраняет накладные расходы на динамическую диспетчеризацию в рантайме и предотвращает состояние гонки (data races) на этапе компиляции.

### Ключевые архитектурные столпы
1. **Уникальность через запрет копирования (`~Copyable`)**: Ограничение побитового копирования памяти на этапе компиляции предотвращает случайное дублирование низкоуровневых примитивов блокировки. Это исключает неопределенное поведение планировщика ядра ОС и дефекты состояния гонки.
2. **Статическое сглаживание полиморфизма (`associatedtype`)**: Контейнеры хранения изолируют политики синхронизации с помощью статических требований к типам, а не через рантайм-обертки экзистенциальных типов (`AnyObject`). Это позволяет компилятору полностью инлайнить (`@inline(__always)`) структуры блокировок прямо в прикладные циклы приложения.
3. **Режим итерации со сбросом лока (Lock Dropping)**: Механизмы последовательного обхода коллекций используют агрессивную стратегию сброса разделяемой блокировки чтения. Лок удерживается исключительно на время считывания и буферизации указателя текущего элемента, после чего полностью отпускается до того, как сработает замыкание пользователя или хуки очистки ресурсов. Это предотвращает инверсию приоритетов, голодание потоков и каскадные взаимоблокировки (deadlocks) между модулями.

## 1. Контракты структурного макета протоколов

### `Locking`
Высокопроизводительная спецификация взаимного исключения (мьютекса), обеспечивающая монопольное владение ресурсом в рамках уникальных границ заимствования (`borrowing`).

```swift
public protocol Locking: Sendable, ~Copyable {
    init()

    /// Захватывает лок монопольно. Блокирует вызывающий поток, если лок уже удержан.
    borrowing func lock()

    /// Освобождает монопольный лок.
    borrowing func unlock()

    /// Пытается захватить монопольный лок без блокировки вызывающего потока.
    /// - Returns: `true`, если лок успешно захвачен; иначе `false`.
    borrowing func lockIfAvailable() -> Bool
}
```

### `RWLocking`
Высокопроизводительный контракт разделяемо-эксклюзивной синхронизации, обеспечивающий параллельное чтение из нескольких потоков одновременно, но строго изолирующий мутации состояния за одним вектором записи.

```swift
public protocol RWLocking: Sendable, ~Copyable {
    init()
    borrowing func readLock()
    borrowing func writeLock()
    borrowing func unlock()
    borrowing func tryReadLock() -> Bool
    borrowing func tryWriteLock() -> Bool
}
```

### Связи макета контейнера (`HasLock` & `HasRWLock`)
Устанавливают четкие границы владения конкретным типом блокировки внутри структур данных.

```swift
public protocol HasLock: AnyObject {
    associatedtype Lock: Locking
    var lock: Lock { get }
}

public protocol HasRWLock: AnyObject {
    associatedtype Lock: RWLocking
    var lock: Lock { get }
}
```

## 2. Низкоуровневые реализации примитивов

### `AdaptiveSpinLock`
Быстрый дженерик-лок, который динамически балансирует между активным софтверным спин-локом (spin-loop) в User-space и безопасным усыплением потока в ядре ОС. Он использует **инвертированные профили конкуренции** для автоматической настройки стратегии ожидания на основе плотности потоков.

* **Аксиома высокой конкуренции (High Contention)**: В условиях жесткой перегрузки данными активный спин-лок разрушителен из-за непрерывного выбивания кэш-линий процессора (Cache Line Bouncing). Замок снижает лимит попыток спина при высокой нагрузке, оперативно паркуя потоки в системные очереди ожидания ядра ОС, чтобы держать общую системную шину памяти CPU чистой для работающего потока.

```swift
public protocol SpinThreshold {
    static var attemptsMax: UInt { get }
}

/// Для изолированных сред с нулевым риском столкновения потоков. Максимальный спин в User-space.
public enum LazyContention: SpinThreshold { public static var attemptsMax: UInt { 10000 } }

/// Сбалансированный профиль для стандартных распределенных нагрузок в приложении.
public enum NormalContention: SpinThreshold { public static var attemptsMax: UInt { 1000 } }

/// Для высоконагруженных общих ресурсов. Быстрый выход из спина во избежание перегрузки шины.
public enum HeavyContention: SpinThreshold { public static var attemptsMax: UInt { 100 } }

/// Точки экстремального параллельного трафика. Мгновенная блокировка для предотвращения троттлинга CPU.
public enum ExtremeContention: SpinThreshold { public static var attemptsMax: UInt { 10 } }
```

#### Геометрия памяти и профиль аллокации
`AdaptiveSpinLock` обеспечивает **нулевую стоимость хранения (Zero-Cost Storage Layout)**. Он не хранит никаких полей состояния для трекинга лимитов на уровне экземпляра класса. Значение порога `T.attemptsMax` вычисляется как константа времени компиляции и внедряется оптимизатором LLVM напрямую в регистры процессора (`MOV` инструкции) на этапе сборки.

### `PosixRWLock`
Строгая POSIX-совместимая реализация, оборачивающая `pthread_rwlock_t` внутри структуры `final class`. Ссылочный тип класса гарантирует абсолютно стабильный адрес расположения примитива в памяти, исключая дефекты смещения данных и позволяя безопасно использовать прямые указатели внутри немутирующих протокольных требований `borrowing`.

### `VoidRWLock`
Фиктивный (dummy) синхронизационный примитив с нулевой стоимостью, полностью пропускающий любые инструкции блокировок. Предназначен для использования в качестве эталона в бенчмарках производительности и оптимизации конвейеров, гарантированно работающих в однопоточном режиме.

## 3. Анализ профиля производительности железа

Архитектура синхронизации была протестирована на аппаратной матрице Apple Silicon `arm64e` под управлением сериализованного сьюта бенчмарков (500 000 плотных мутаций границ и 8 000 000 параллельных итераций чтения по цепочке из 100 000 элементов).

### Однопоточный профиль записи (от 0 до 500 000 добавлений)

| Тип примитива | Длительность (Секунды) | Эффективность выполнения относительно `VoidRWLock` |
| :--- | :--- | :--- |
| `VoidRWLock` | **0.229с** | *Базовый уровень (100% идеальная скорость без локов)* |
| `OSAllocatedUnfairLock` | **0.230с** | +0.43% (Околонулевые накладные расходы железа) |
| `PosixRWLock` | **0.235с** | +2.62% |
| `AdaptiveSpinLock<Normal>` | **0.234с** | +2.18% (Оптимизированный плоский цикл `while` на регистрах) |

#### Инженерные инсайты:
* **Микрооптимизация `while` против `for-in`**: Перенос софтверной фазы спина из стандартного диапазона `for-in` в плоское условие `while` сократил накладные расходы с **0.330с** до **0.234с**. Эта оптимизация убрала неявное создание итераторов `IndexingIterator` и проверки границ диапазонов, вернув коду чистую скорость языка Си.
* **Нативный быстрый путь**: В отсутствие конкуренции за данные нативный `os_unfair_lock` выполняет одну легкую атомарную инструкцию `LDREX`/`STREX` прямо в кэше L1 процессора, обеспечивая скорость, идентичную потоко-небезопасному коду.

### Параллельный профиль конкурентного чтения (4 потока × 5 полных обходов)

| Тип примитива | Длительность (Секунды) | Уязвимость архитектуры при экстремальном трафике |
| :--- | :--- | :--- |
| `VoidRWLock` | **0.447с** | Потоко-небезопасно (Только симуляция) |
| `OSAllocatedUnfairLock` | **0.786с** | Умеренная конкуренция за шину памяти |
| `PosixRWLock` | **1.072с** | Оверхед атомарного счетчика читателей в POSIX |
| `AdaptiveSpinLock<Normal>` | **1.354с** | Жесткое выбивание кэш-линий процессора |

#### Инженерные инсайты:
* **Почему `OSAllocatedUnfairLock` обошел Reader-Writer мьютекс**: На сверхкоротких критических секциях (где мы в режиме Lock Dropping просто копируем указатель на следующую ноду), накладные расходы `pthread_rwlock_rdlock` на атомарный учет количества читателей, проверку очереди писателей и распределение билетов становятся дороже самого лока. Легковесный unfair-лок из User-space щелкает такие циклы с гораздо меньшей латентностью.
* **Почему `AdaptiveSpinLock` просел под нагрузкой**: Экстремальная плотность вызовов заставила все 4 ядра процессора одновременно зайти на фазу активного аппаратного спина. Это привело к эффекту **Cache Line Bouncing** — процессор тратил колоссальное количество тактов на синхронизацию состояния памяти между ядрами, что добавило 0.5 секунды задержки относительно нативного unfair-лока.

## 4. Руководство по интеграции

Чтобы назначить кастомный примитив синхронизации для контейнера данных `SwanCore`, укажите целевой лок при объявлении дженерик-границ структуры:

```swift
// Продакшн-конфигурация: максимальный разгон и латентность на актуальных платформах Apple
let platformSecureList = List<Int, OSAllocatedUnfairLock>()

// Высоконагруженный общий ресурс: жесткий контроль спина на уровне регистров процессора
let highlyConcurrentList = List<String, AdaptiveSpinLock<HeavyContention>>()

// Однопоточная песочница/бенчмарк: полное отключение локов на этапе компиляции
let sandboxedBenchmarkList = List<Double, VoidRWLock>()
```
